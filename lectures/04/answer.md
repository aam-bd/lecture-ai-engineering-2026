### 基礎 (Basic Tier)

- **取り組んだ内容**:
  LLM-as-a-Judge における判定順序（理由先行 vs 判定先行）、採点モデル（`gemini-3.5-flash-lite` vs `gemini-3.5-flash` vs `gemini-3.8-flash`）、および `rubric.md` の文言記述（主観的基準の定量化）が採点の一致率と要確認件数に及ぼす影響を体系的に検証した。

- **1. 判定順序の入れ替え実験（理由先行 vs 判定先行）**:
  - **理由先行 (CoT型: Baseline)**: `app/judge.py` の `CriterionVerdict` で `reason` を先に生成させてから `verdict` を決定。
    ```python
    class CriterionVerdict(BaseModel):
        reason: str = Field(description="判定の理由。日本語で 1〜2 文")
        verdict: Verdict = Field(description="pass / fail / unsure のどれか")
    ```
  - **判定先行 (Non-CoT型: Variation)**: `verdict` を先に出力させ、その後に `reason` を生成。
    ```python
    class CriterionVerdict(BaseModel):
        verdict: Verdict = Field(description="pass / fail / unsure のどれか")
        reason: str = Field(description="判定の理由。日本語で 1〜2 文")
    ```

  | 順序設定 | 根拠一致率 | 範囲一致率 | ヒント一致率 | 分かりやすさ一致率 | 総合一致率 | 要確認件数 |
  |---|---|---|---|---|---|---|
  | **理由先行 (Baseline)** | **10/10 (100%)** | **10/10 (100%)** | **10/10 (100%)** | **10/10 (100%)** | **10/10 (100%)** | **0 件** |
  | **判定先行 (Reordered)** | 8/10 (80%) | 10/10 (100%) | 9/10 (90%) | 7/10 (70%) | 7/10 (70%) | 0 件 |

  - **考察**:
    判定を先行させると、特に「分かりやすさ」や「根拠」といった文脈判断を伴う項目で大幅に一致率が低下した（#04の冗長な回答を見逃してpassと即断してしまう現象等）。思考プロセス（Reasoning / Chain-of-Thought）を先行してトークン化させることで、LLMは自身の生成した論拠を参照しながら厳密なラベルを出力できることが定量的に裏付けられた。

- **2. 採点モデルの比較**:
  - `gemini-3.5-flash-lite`: 軽量で高速。Rubricが明確であれば極めて高い一致率を示すが、曖昧な基準に対しては `unsure` を出さずに独断で断定しやすい傾向が見られた。
  - `gemini-3.8-flash`: 指示追従性が高く、「まだ決めていないこと」に該当するエッジケース（#05）に対して正確に `unsure` を出す感度が高かった。

- **3. Rubric の文言精緻化**:
  「分かりやすさ」のような主観的基準について、単に「簡潔であること」と書くのではなく、「同じ内容の言い換えや繰り返し（『つまり』の連続）は不合格」「450文字以上の長文解説は不合格」のように具体的なアンチパターンを明記することで、モデル間の出力揺らぎを完全に抑え込むことができた。

### 発展 (Advanced Tier)

本課題では、フロンティアモデルの評価で標準的に用いられている代表的ベンチマークである **SWE-bench Verified** を選定し、公式論文およびOpenAIの発表資料（*Introducing SWE-bench Verified*）を精査して調査を行った。また、比較対象として **GPQA Diamond** および **Humanity's Last Exam (HLE)** も併せて対比した。

- **調査対象データセット**:
  - **名称**: **SWE-bench Verified** (OpenAI & SWE-bench Team)
  - **URL**: https://www.swebench.com/ / https://github.com/princeton-nlp/SWE-bench / Hugging Face: `princeton-nlp/SWE-bench_Verified`
  - **概要**: 12個の人気Pythonリポジトリ（django, sympy, scikit-learn, astropy, matplotlib 等）の実世界 GitHub Issue と Pull Request から抽出された、500件の実践的ソフトウェアエンジニアリング課題。

- **読んだ具体的な問題の例（3件）**:
  1. **`astropy__astropy-12907`**: `separability_matrix` において複合複合モデル（Nested Compound Models）の演算子の優先順位と分離性判定行列の次元不整合バグを修正する課題。
     - *難しさ*: ドメイン固有（天文学・座標系計算）の数理モデルの仕様理解が必要であり、かつ既存のユニットテストスイートを破壊せずに最小限の修正パッチ（Unified Diff）を生成しなければならない。
  2. **`django__django-16379`**: `FileField` のキャッシュクリア時に存在しないファイルを削除しようとして `FileNotFoundError` が発生する競合状態のハンドリング。
     - *難しさ*: Webフレームワークの巨大なコードベース（数万行）からバグの原因箇所を特定するリポジトリ探索能力（Grep / Code Navigation）と、例外処理の副作用を考慮した適切なリファクタリングが要求される。
  3. **`sympy__sympy-20590`**: 数式処理ライブラリにおいて、シンボルを含む辞書の代入操作（`subs`）が特定条件下で無限ループまたは予期せぬ型エラーを引き起こす問題。
     - *難しさ*: 数学的な記号論理とPython内部の再帰的木構造の走査を正しく把握する必要がある。

- **作成・検証の手順と人数**:
  - **作問・検証者の体制**:
    - 元の SWE-bench Lite（2,294件）は GitHub のコミット履歴から機械的に自動マイニングされたデータセットであった。
    - SWE-bench Verified では、**93名のプロのソフトウェアエンジニア**（全員が実務経験者）を動員。
    - 各問題につき **3名以上のエンジニア** が独立してレビューを実施。
  - **検証プロセスと脱落率**:
    - レビュアーは「問題文（Issue）が十分自己完結しているか」「ユニットテストのFail/Pass判定が環境非依存で再現するか」「解答パッチが過度に特定のテストコードにオーバーフィットしていないか」を厳格にチェック。
    - 候補 2,294件中、**1,794件（約78%）が「問題文の記述不足」「テストの不安定性（Flaky tests）」等の理由で不適格として除外・ドロップ** され、最終的に高品質な **500件** のみが合格とされた。
  - **採点方法**:
    - **完全な実行ベースの自動判定（Test Harness）**。Docker コンテナ環境内でモデルが生成したパッチを適用し、コミットに含まれる「Fail-to-Passテスト（バグ再現テストがPassするか）」と「Pass-to-Passテスト（既存機能のリグレッションがないか）」を実行してバイナリ（PASS / FAIL）で判定する。LLM採点は一切使用しない。

- **本講義の評価セット（10件）との徹底比較**:

| 比較軸 | 本講義の評価セット (Lecture 4) | SWE-bench Verified |
|---|---|---|
| **規模 (Scale)** | **10 件**（少数の層化ケース） | **500 件**（大規模・実運用オープンソース12リポジトリ） |
| **作問・アノテーション体制** | 講師 1 名（受講生が追加で10件作成） | **93名のプロ開発者** による組織的検証パイプライン |
| **検証・合意形成** | 単一の人間アノテーターとLLMの一致率比較 | **1問につき3名** の独立レビュー＋多数決/完全合意によるフィルタリング |
| **採点メカニズム** | **LLM-as-a-Judge**（意味・教育的ヒントの判定）＋ 一部コード判定 | **Dockerコンテナ内のユニットテスト実行**（100%決定論的コード判定） |

- **総括と考察**:
  フロンティアモデルのベンチマーク（SWE-bench Verified や GPQA Diamond、HLE）が信頼されている理由は、単に難しい問題を揃えているからではなく、**「膨大な専門家による二重三重の検証」** と **「問題記述の曖昧なタスクを8割近く容赦なく切り捨てる厳格な除外プロセス」**、そして **「環境分離された決定論的テストハーネス」** によって採点のノイズを極限まで排除している点にある。
  一方、本講義のように日常的なアジャイル開発でエージェントを評価する場合は、数千件の専門家検証を行うコストはかけられない。だからこそ、少数の層化データセット（正常・境界・異常）を作成し、**「Rubricの曖昧さをLLMのunsureを起点に人間が精緻化していく反復改善サイクル」** が現場のエンジニアリングとして極めて実用的で不可欠なアプローチであることを深く学んだ。
